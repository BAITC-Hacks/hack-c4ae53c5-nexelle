# Career Quest - план разработки

## 1. Цель MVP

Собрать веб-приложение Career Quest для сотрудника и HR. Сотрудник открывает профиль, видит целевой карьерный уровень, пробелы в навыках, 1-3 доступных добровольных шага развития с объяснением и обновлённый прогресс после завершения. HR видит агрегированный срез навыков, вовлечённости и сотрудников без следующего шага.

Главный критерий MVP - качество и проверяемость рекомендации. Геймификация, витрина наград и публичные рейтинги в MVP не входят.

## 2. Что учтено из брифа и датасета

| Факт | Решение в плане |
|---|---|
| 200 сотрудников, 8 ролей, 4 грейда | В движке есть профиль цели для каждой пары `role + grade`; карьерная цель сотрудника может вести и в другую роль. |
| 60 навыков: 46 hard и 14 soft | Прогресс и пробелы рассчитываются по `skill_id`, а не по названию или одному типу навыков. |
| Требования роли содержат 7-16 навыков, из них 1-3 критических | Критическим навыкам назначается повышенный вес при ранжировании. |
| 40 мероприятий: 4 обязательных, 36 добровольных; у 12 есть prerequisites | Обязательные мероприятия не рекомендуются. Кандидат проходит фильтр аудитории, пререквизитов, расписания и повторного прохождения. |
| 9 self-paced и 31 мероприятие с будущими сессиями | Доступность влияет на итоговый балл: self-paced доступно сразу, сессии выбираются после даты среза. |
| 2 743 записи истории | Учитываются завершения, пропуски, отказы, незавершённые и просроченные активности; однофакторный выбор «самого слабого навыка» запрещён. |
| В истории 2 178 completed, 195 no_show, 160 dropped, 104 declined | Повторные пропуски/отказы по похожим активностям понижают приоритет, но не скрывают критичный карьерный разрыв. |
| 134 сотрудника имеют карьерную цель, 66 - нет | При цели используется её профиль; без неё строится следующий грейд текущей роли. Для Lead показывается поддержание текущего профиля и предложение зафиксировать цель, а не выдумывается повышение. |
| Предпочитаемые языки: ru - 100, kk - 89, en - 11 | Контент и DTO должны поддерживать локализацию. На демо минимум нужны ru и kk для интерфейса; технические названия навыков не должны мешать объяснению. |
| Жюри загрузит дополнительные профили и историю в той же схеме | Импорт не зависит от захардкоженных 200 сотрудников и валидирует JSON/CSV по исходной схеме. |

Дата среза данных: `2026-10-01`. Она передаётся в расчёт явно, а не берётся из системных часов.

## 3. Граница MVP

### Обязательно к защите

- Загрузка `skills.json`, `employees.json`, `events.json` и `activity_history.csv`; отдельная загрузка проверочных профилей и истории.
- Профиль сотрудника: роль, грейд, карьерная цель/следующий грейд, навыки, история активностей, прогресс до цели.
- 1-3 добровольные рекомендации и объяснение минимум по трём факторам.
- Отметка «завершено»: создаёт/обновляет запись истории, применяет `gain` с ограничением `max_level`, пересчитывает навыки, траекторию и рекомендации.
- HR-view: наиболее частые пробелы относительно целей, отсутствие доступной рекомендации, участие/завершение по мероприятиям.
- Разделение ролей `employee` и `hr` в API и интерфейсе; сотрудник не видит данные коллег.
- README с одним способом запуска, примерами сценариев и ограничениями данных.

### После работающего MVP

- Качественная локализация всех объяснений на ru/kk.
- Небольшая приватная геймификация: личные вехи и серии завершений, без общего лидерборда.
- Прогноз риска выпадения, расширенная аналитика HR, календарь/мессенджер и витрина наград.

## 4. Логика рекомендации

### 4.1 Подготовка профиля

1. Загрузить и провалидировать связи между файлами.
2. Взять оценённые навыки сотрудника на дату `last_review_date`.
3. Применить к ним только завершённые после этой даты мероприятия из истории: `new = min(current + gain, max_level)`. Активности без развиваемых навыков не меняют профиль.
4. Определить цель: `career_goal`, если она задана и есть в `role_profiles`; иначе следующий грейд той же роли.
5. Для каждого навыка цели посчитать разрыв `max(required - effective_level, 0)` и отметить критичность.

### 4.2 Фильтр кандидатов

В рекомендацию попадает только мероприятие, которое:

- не `mandatory`;
- предназначено для текущей роли/грейда или явной карьерной цели;
- имеет выполненные prerequisites;
- доступно как `self_paced` или имеет будущую сессию после даты среза;
- не завершено ранее этим сотрудником; исключение - повторяемый клуб `EV_036`;
- развивает хотя бы один навык с ненулевым разрывом.

### 4.3 Ранжирование и объяснимость

Для каждого кандидата сохранить разложение итогового балла, а не только число. Стартовая формула для настройки на проверочных профилях:

| Компонент | Смысл |
|---|---|
| Покрытие пробелов | Сумма закрываемых разрывов с повышенным весом критических навыков. |
| Близость к цели | Насколько мероприятие соответствует роли и целевому грейду. |
| История участия | Завершения повышают доверие к формату/теме; похожие no_show, dropped и declined понижают его. |
| Выполнимость | Формат, ближайшая сессия и длительность помогают выбрать реалистичный следующий шаг. |
| Разнообразие | В топ-3 не дублировать один и тот же навык или формат, если есть сопоставимая альтернатива. |

Объяснение должно содержать факты из сохранённого разложения: текущий и требуемый уровень навыка, критичность/цель, историю участия и доступность. Пример: «System Design: 2 из 4 для Senior; навык критичен для цели; этот формат вы раньше завершали; следующая сессия доступна ...».

LLM допустимо использовать только как слой естественного изложения этих уже вычисленных фактов и перевода. Он не выбирает мероприятие и не получает права придумывать причины. При недоступности модели показывается шаблонное объяснение с теми же доказательствами. Это сохраняет объяснимость, воспроизводимость и укладывает интерфейсный отклик до 2 секунд; генерация текста может выполняться в лимите 10 секунд.

### 4.4 Проверка на сценарии жюри

Отдельный тест обязан покрыть пример из задания: слабый Public Speaking не должен автоматически победить критичный разрыв System Design, если в истории есть три пропуска похожих активностей. Тест должен доказывать, что итог ранжирования использовал как минимум цель/грейд, разрывы и историю.

## 5. Минимальная архитектура и контракты

Финальные фреймворки, БД, способ запуска и LLM-провайдер команда утверждает на старте. Независимо от выбора стека границы компонентов остаются такими:

```text
JSON / CSV importer --> validated data store --> progress calculator
                                              --> recommendation engine --> evidence
employee / HR UI <--> role-aware API <-----------------------------------+
                                              --> explanation adapter (LLM or template)
```

Контракт рекомендации должен возвращать не только `event_id`, но и `score_breakdown`, `skill_gaps`, `eligibility`, `history_signals` и локализуемый текст объяснения. Контракт обновления прогресса должен возвращать изменённые навыки и свежую рекомендацию в одном ответе.

Рекомендуемые сценарии API для согласования до начала кодирования:

- получить список/профиль сотрудника и его траекторию;
- получить рекомендации;
- отметить мероприятие завершённым;
- получить HR-агрегаты;
- загрузить дополнительный профиль и записи истории с отчётом валидации.

## 6. Разделение работы на троих

| Участник | Зона ответственности и результат | Границы файлов |
|---|---|---|
| 1. Backend и данные | Доменные модели, импорт и валидация четырёх файлов, хранилище, role-aware API, загрузка проверочных профилей, базовая аутентификационная роль для демо. Результат: сервис отдаёт профиль, историю, каталог и HR-агрегаты. | `cmd/`, `internal/importer/`, `internal/store/`, `internal/transport/` |
| 2. Recommendation и AI | Чистый движок эффективных навыков, расчёт траектории, eligibility, ранжирование, evidence DTO, обновление после completion, адаптер LLM/шаблонного объяснения и юнит-тесты на кейс жюри. Результат: детерминированный топ-3 с доказательствами. | `internal/progress/`, `internal/recommendation/`, `internal/explanation/` |
| 3. UX, HR и demo-ready | Экран сотрудника, карточки рекомендации и доказательств, действие completion, HR-dashboard, ru/kk-словарь UI, визуальное разделение ролей, e2e-проверка, README, demo-сценарий и конфигурация запуска. Результат: демонстрируемый путь сотрудника и HR без ручной подмены данных. | `web/` или отдельный UI-пакет, `docs/`, `README.md`, конфигурация запуска |

До первого коммита участники согласуют DTO в коротком API-контракте. Участник 2 не зависит от HTTP: его вход - доменные структуры, выход - рекомендации с evidence. Участник 3 начинает на mock-ответах и переключается на API после появления контракта. Это уменьшает конфликты в общих файлах.

## 7. Порядок работы

### Этап 0 - первые 60 минут

1. Утвердить стек и способ запуска одной командой.
2. Зафиксировать MVP выше, API DTO и состояние хранения прогресса.
3. Выбрать один показательный профиль и подготовить сценарий «до -> рекомендация -> completion -> после».

### Этап 1 - параллельная основа

- Участник 1: импорт, валидация, доменные сущности, черновой API.
- Участник 2: эталонные функции расчёта навыков, фильтра и scoring с тестами на реальных данных.
- Участник 3: макет двух ролей, карточка рекомендации, mock API и локализация строк.

Критерий готовности: один сотрудник из стартового набора открывается в интерфейсе и имеет воспроизводимый расчёт пробелов.

### Этап 2 - сквозной сценарий

- Соединить UI с API и recommendation engine.
- Реализовать completion и мгновенный пересчёт прогресса.
- Добавить HR-агрегаты и представление отсутствия рекомендации.
- Подключить LLM-адаптер только после того, как шаблонное evidence-объяснение уже корректно.

Критерий готовности: каждый must-have проходится без ручного изменения данных.

### Этап 3 - защита и воспроизводимость

1. Прогнать три загруженных профиля жюри и сохранить результаты проверки.
2. Проверить отсутствие рекомендации, Lead без цели, prerequisites, повторное завершение и `EV_036`.
3. Проверить разграничение employee/HR и отсутствие данных коллег в employee API.
4. Подготовить README: запуск, загрузка данных, demo-данные, API и ограничения.
5. Отрепетировать демонстрацию: проблема -> профиль -> объяснение трёх факторов -> completion -> HR-срез -> проверочный профиль.

## 8. Definition of Done

- Новый профиль и история, соответствующие исходной схеме, загружаются без изменений кода.
- На экране доступны роль, грейд, цель, навыки, история и 1-3 объяснимых шага.
- В каждом объяснении присутствуют не менее трёх фактов из `evidence`.
- Завершение обновляет навыки строго по `gain` и `max_level`, после чего меняются прогресс и рекомендации.
- HR видит агрегаты, а сотрудник - только собственные данные.
- Автотесты покрывают фильтр, scoring, лимит навыка, запрет повторов и контрпример из задания.
- Проект форматируется, собирается и запускается по README одной командой.

## 9. Решения, которые нужно принять командой на старте

- Фронтенд: отдельное SPA или серверные шаблоны.
- Хранилище для демо: файлы/память или БД; оно должно переживать completion на время демонстрации.
- LLM-провайдер и ключ: только через переменные окружения, с шаблонным fallback.
- Способ запуска и деплой: один воспроизводимый сценарий для жюри.
- Механика входа для демо: безопасное переключение тестовых ролей без имитации production-аутентификации.
